TypeScript principles
- No any types unless absolutely necessary.
- Check node_modules for external API type definitions instead of guessing.
- Prefer SDK-provided types, schemas, helpers, and model metadata over local redefinitions. For things like Cline SDK reasoning settings, use the SDK's source of truth whenever possible instead of recreating unions, support checks, or shapes in Kanban.
- NEVER use inline imports. No await import("./foo.js"), no import("pkg").Type in type positions, and no dynamic imports for types. Always use standard top-level imports.
- NEVER remove or downgrade code to fix type errors from outdated dependencies. Upgrade the dependency instead.

Code quality
- Write production-quality code, not prototypes
- Break components into small, single-responsibility files. 
- Extract shared logic into hooks and utilities. 
- Prioritize maintainability and clean architecture over speed. 
- Follow DRY principles and maintain clean architecture with clear separation of concerns.
- In `web-ui`, prefer `react-use` hooks (via `@/kanban/utils/react-use`) whenever possible
- Before adding custom utility code, evaluate whether a well-maintained third-party package can reduce complexity and long-term maintenance cost.

Architecture opinions
- Avoid thin shell wrappers that only forward props or relocate JSX for a single call site.
- Prefer extracting domain logic (state, effects, async orchestration) over presentation-only pass-through layers.
- Do not optimize for line count alone. Optimize for codebase navigability and clarity.

Git guardrails
- NEVER commit unless user asks.

GitHub issues
When reading issues:

  gh issue view <number> --json title,body,comments,labels,state

When closing issues via commit:

web-ui Stack
- Kanban web-ui uses Tailwind CSS v4 for styling, Radix UI for accessible headless primitives, and Lucide React for icons.
- Custom UI primitives live in `src/components/ui/` (button, dialog, tooltip, kbd, spinner, cn utility).
- Toast notifications use `sonner`. Import `{ toast }` from `"sonner"` or use `showAppToast` from `@/components/app-toaster`.

Styling mental model
- Use Tailwind utility classes as the primary styling system. Prefer `className` over inline `style={{}}`.
- Prefer Tailwind classes over adding custom CSS in `globals.css` when possible. Conditional Tailwind classes via `cn()` are better than CSS overrides for state-driven styling (e.g. selected/active variants). Reserve `globals.css` for things Tailwind can't express: complex selectors (sibling combinators, attribute selectors), app-level layout glue, or styles that genuinely need to cascade.
- Only use inline `style={{}}` for truly dynamic values (colors from props/variables, computed positions from drag-and-drop, runtime-dependent dimensions).
- The design system tokens are defined in `globals.css` inside `@theme { ... }`. Use Tailwind utilities that reference them: `bg-surface-0`, `text-text-primary`, `border-border`, etc.

Dark theme
- The app is always in dark theme. Colors are set via CSS custom properties in `globals.css`.
- Surface hierarchy: `bg-surface-0` (app background) -> `bg-surface-1` (raised panels) -> `bg-surface-2` (cards/inputs) -> `bg-surface-3` (hover) -> `bg-surface-4` (pressed).

Misc. tribal knowledge
- Kanban's native Cline agent is powered by the installed `@clinebot/core` and `@clinebot/llms` packages plus the local `src/cline-sdk/` boundary layer, so when Cline behavior is unclear, inspect those packages and `src/cline-sdk/` for the real implementation details.
- Kanban is launched from the user's shell and inherits its environment. For agent detection and task-agent startup, prefer direct PATH checks and direct process launches over spawning an interactive shell. Avoid `zsh -i`, shell fallback command discovery, or "launch shell then type command into it" on hot paths. On setups with heavy shell init like `conda` or `nvm`, doing that per task can freeze the runtime and even make new Terminal.app windows feel hung when several tasks start at once. It's fine to use an actual interactive shell for explicit shell terminals, not for normal agent session work.
- Kanban's inherited PATH is the single source of truth for both agent detection and agent spawns. A binary that is only on PATH after interactive shell init (for example `sf` at `~/.local/share/pnpm/bin/sf` added by `~/.zshrc`) is intentionally reported as not installed. The supported escape hatch is the opt-in `agentPathPrepend` / `agentEnv` keys in `~/.cline/kanban/config.json`, resolved by `src/config/agent-runtime-env.ts` and applied to both `isBinaryAvailableOnPath` and the PTY launch env. Do not "fix" a missing agent binary by spawning an interactive shell; extend the shared helper instead.
- Native Cline `run_commands` is hard-coded to a 30s timeout inside `@clinebot/core` 0.0.38, in both the tool-level race and the spawned process executor, and no `CLINE_*TIMEOUT*` env var or session setting exists. Kanban overrides it with `agentCommandTimeoutSec` (`~/.cline/kanban/config.json`, Settings -> Command timeout): `src/cline-sdk/sdk-runtime-boundary.ts` rebuilds the tool through the SDK's own `createDefaultExecutors` / `createDefaultTools` factories and `cline-session-runtime.ts` registers it last in `localRuntime.extraTools`. Core composes tools as `[...builtins, ...extraTools]` and `@clinebot/agents` stores them in a name-keyed Map, so the last duplicate wins for both the model-visible schema and execution. Delete the override once upstream threads `bashTimeoutMs` through session config.
- If CI hangs on Node 22 after tests seem to finish, suspect a live subprocess or SDK-host startup path before assuming a slow test body. Read `.plan/docs/node22-ci-hanging-tests-investigation.md` before repeating that investigation. `test/runtime/cline-sdk/cline-task-session-service.test.ts` was the big prior culprit because a unit-style suite was still booting the real Cline SDK host.
- `pnpm test` is deliberately the FAST path (`test:fast` = `test/runtime` + `test/utilities`, ~603 tests / ~5s) and EXCLUDES `test/integration`. Do not "restore" it to `vitest run`. The integration suite spawns a real CLI/server subprocess and boots a fresh process per scenario (~2s each), so it is ~45s of mostly serial cold starts; `test/integration/runtime-state-stream.integration.test.ts` alone does 14 boots across 11 tests and is the slowest file in the repo. Use `pnpm test:all` for everything, `pnpm test:integration` for just the integration suite (CI runs these as separate steps). `pnpm run check` / `prepublishOnly` intentionally uses `test:all`, so publishing still requires integration coverage. Note that raising the spawned-server startup timeout is NOT enough on its own: each integration test also has its own per-test timeout, and the boot budget must stay below it or the test dies with vitest's generic timeout instead of the harness's useful one.
- Splitting a slow integration file into multiple files to "parallelise" it makes `pnpm test` SLOWER, not faster. Vitest computes `maxWorkers` from CPU count, not from the subprocesses tests spawn, so extra files just create more concurrent out-of-band server boots competing for the same cores, while each file re-pays the full module-graph setup. Measured: capping `--maxWorkers` (8 vs 15) and splitting both failed to help; the run is bound by the serial chain of ~2s cold starts, so the only real lever is per-boot cost (which is why `src/cli.ts` keeps telemetry imports lazy).
- Native Cline task summaries are owned by `ClineTaskSessionService`, not `TerminalSessionManager`. Do not hydrate `agentId: "cline"` summaries into the PTY manager: a stale persisted summary would override the live Cline service for the rest of the process. Startup reconciliation marks persisted Cline `running` sessions interrupted from workspace state directly, then lets the Cline service own any live state.
- When Kanban runs on a headless remote Linux instance (for example over SSH+tunnel), native folder picker commands may be unavailable (`zenity`/`kdialog`). Treat this as a normal remote-runtime limitation and use manual path entry fallback instead of requiring desktop packages.
- Do not early-return a full-page fallback from `App.tsx` for a transient runtime disconnect. Replacing the app tree unmounts every composer and terminal surface, which is why unsent prompts used to disappear on a Cloudflare-tunnel blip. Keep the shell mounted once a snapshot has loaded and show `RuntimeDisconnectedFallback variant="overlay"` instead; unsent chat/new-task drafts are also persisted in `web-ui/src/storage/text-drafts.ts` so a real reload can restore them.
- Persistent task-terminal reconnects must reopen the whole per-viewer socket pair, not just the IO socket. `src/terminal/ws-server.ts` only clears a viewer's `restoreComplete` gate and re-sends the `restore` snapshot when the control socket connects, so reconnecting IO alone leaves the client waiting for a restore that never arrives. `web-ui/src/terminal/persistent-terminal-manager.ts` therefore tears down both sockets on any abnormal close and reconnects them together.
- A `404 Unknown workspace ID: <id>` from the runtime is almost never a bad workspace id - it means workspace resolution failed. Every workspace-scoped tRPC request resolves its id through `loadWorkspaceScopeById` (`src/state/workspace-state.ts`), which must stay lock-free and must not spawn git. The historical failure was `loadWorkspaceContext` taking the global `~/.cline/kanban/workspaces/index.json` write lock and running 4-5 `spawnSync` git probes inside it, so concurrent requests (e.g. clicking Commit while state/git queries are in flight) exhausted the `proper-lockfile` retry budget (~5-10s), `ELOCKED` was swallowed by a bare `catch { return null }`, and the client was told the workspace did not exist. Keep read paths off that lock, probe git outside it, and catch only `WorkspaceUnavailableError` when mapping a failure to "not found".
- `loadWorkspaceState` (and the old `loadWorkspaceStateById`) is not a polling primitive: it builds the git metadata via `detectGitRepositoryInfo`, which is four `spawnSync("git", ...)` calls, so every call blocks the runtime's event loop. The auto-review reconciler (`src/server/auto-review-reconciler.ts`) therefore reads the board with `loadWorkspaceBoardById` - one `readFile` + parse, no subprocess, no lock. When a new loop needs periodic state, take the narrowest reader that answers the question, and never a helper whose name hides a subprocess.
- `src/server/runtime-state-hub.ts` sends the initial `snapshot` frame *before* registering the socket in `runtimeStateClientsByWorkspaceId` (deliberate, so `workspace_metadata_updated` cannot race the snapshot). A workspace-scoped broadcast issued right after the snapshot can therefore be silently dropped. Tests that connect a client then broadcast must prove registration happened instead of sleeping: probe with `broadcastTaskReadyForReview` (same per-workspace fan-out, sends immediately) until a frame lands. Otherwise the test fails as "broadcast never arrives" and looks like a hub bug. The helper lives in `test/runtime/server/runtime-state-hub.test.ts`.
- `applyAgentRuntimeEnv` (`src/config/agent-runtime-env.ts`) rebuilds `PATH` with Node's `delimiter`, which is host-dependent (`:` on POSIX, `;` on Windows). So a test that fakes `platform = "win32"` and expects `src/core/windows-cmd-launch.ts` to resolve a bare binary out of a `;`-separated PATH cannot work on a POSIX host once `agentPathPrepend` is configured: the rebuilt `:`-joined PATH collapses into a single `;`-separated entry, resolution fails, and `shouldUseWindowsCmdLaunch` falls back to `cmd.exe`. Such a test passes only on a machine with an empty config, so gate it on a real Windows host (`it.skipIf(!isWindows)`), as `test/runtime/terminal/pty-session.test.ts` does. Cases that only assert argument construction stay ungated - they hold on any host.
- Queued prompts and the composer's stop button are two different SDK mechanics, and the composer had conflated them: one button switched between "send" and "pause", so a mouse user could not queue a prompt while the agent was running even though `sendTaskSessionInput` already sends `delivery: "queue"` in that state. The composer now renders a separate Stop button (`cancelTaskTurn` -> `abortTaskSession`) plus a Queue/Send button.
- Queued prompts only *look* delivered when they are actually handed to the agent. Kanban marks the user message `meta.deliveryState: "pending"` when it enqueues (so the transcript can fade it), and the adapter clears that on the SDK's `pending_prompt_submitted` event. Correlate them FIFO, not by prompt text: `resolvePrompt` expands slash commands, so the SDK's submitted prompt is not the stored message content, and the SDK assigns its own pending id after Kanban has already created the message.
- `ClineCore.abort()` clears the SDK's pending prompt queue, so any prompt still shown as pending must be marked `deliveryState: "canceled"` on stop/abort (`emitCanceledQueuedMessages`); otherwise it looks delivered forever. Abort also ends the SDK session, which is why `abortTaskSession` clears the task-session binding and the next send goes through `restartTaskSession` from persisted history.
- A `Retrying: 1 tool call(s) failed: [tool] {"error":"..."}` system message is `@clinebot/core`'s mistake-tracker diagnostic, not an SDK-authored user notice: `MistakeTracker.record` emits an `error` event with `recoverable: true` whose message is the raw `<n> tool call(s) failed: [<tool>] JSON.stringify(toolResult)` string, and `cline-event-adapter.ts` renders it as a chat message. `src/cline-sdk/cline-retry-notice.ts` summarizes it (`malformed tool arguments for <tool>`) and passes unrecognised messages through untouched. Related trap: a tool call whose arguments failed `JSON.parse` is skipped *before* hooks run - `prepareToolExecution` in `@clinebot/agents` sets `skipReason` from `metadata.inputParseError` ahead of the `if (tool && !skipReason)` gate, so `beforeTool` can never repair the arguments; `afterTool` still fires (it only checks `prepared.tool`) and may return `{ result }`, which is where `cline-tool-input-diagnosis.ts` replaces the serialized error with a diagnosis the model can act on. Deepseek models emit `\{` for regex needles, which is not a valid JSON escape.
- A cluster of `TS2607`/`TS2786` (`'Sentry.ErrorBoundary' cannot be used as a JSX component`, "missing the following properties from type 'Component': context, setState, forceUpdate, props, refs") plus implicit-`any` (`TS7006`/`TS7031`) on library-supplied callbacks (`<Droppable>{(provided) => ...}`, `useHotkeys` `ignoreEventWhen`, `useLocalStorage` setters) means the *library's* React typings vanished - not that the code is wrong. Cause: `node_modules/.pnpm/node_modules` (pnpm's hoisted layer) holds broken symlinks into another checkout (`~/.cline/worktrees/<id>/kanban/...`), so packages that `import "react"` without declaring `@types/react` themselves resolve React to the untyped `react/index.js`; `skipLibCheck` suppresses the "no declaration file" diagnostic, so their whole type surface silently becomes `any`. Verify with `find node_modules/.pnpm/node_modules -maxdepth 2 -type l ! -exec test -e {} \; -print` - it must print nothing; `tsc --traceResolution` shows `Module name 'react' was successfully resolved to '.../react/index.js'`. Fix with `rm -rf node_modules/.pnpm/node_modules && pnpm install --frozen-lockfile` (the lockfile is fine and does not need touching), but only when `node_modules` is a real directory: in a provisioned worktree where `node_modules` is itself a symlink to another checkout, that `rm -rf` deletes the shared hoisted layer for every worktree, so relink the dead entries instead (next bullet). Reproduces on TypeScript 5.9 as well as the 7.1 beta, so do not go hunting in the compiler upgrade.
- The same dead-symlink family also lives *outside* `node_modules/.pnpm/node_modules`, and then no test command can even start: `npx vitest` dies with `Cannot find module '<checkout>/web-ui/node_modules/vitest/vitest.mjs'`. In these provisioned worktrees both `node_modules` and `web-ui/node_modules` are symlinks to another checkout's install (shared across worktrees, so `ls -la node_modules` shows a symlink, not a directory), while the package links inside them can still be relative pointers into `.cline/worktrees/<id>/kanban/node_modules/.pnpm/...` for a worktree that has since been deleted. The dead worktree's packages normally already exist in the shared install, so repair the links rather than reinstalling - and never `rm -rf` "inside" the symlinked `node_modules`, because that deletes the shared install out from under every other worktree. Scan recursively (`find <node_modules> -type l ! -exec test -e {} \; -print`; the `-maxdepth 2` check above misses these) and relink each dead entry: take the text after `kanban/node_modules/` in its target, resolve it under `<checkout>/node_modules`, then `unlink` + `symlink`. Do a dry run first and count fixable vs unfixable - 900+ fixable with 0 unfixable means the relink is complete and no network/install is needed.
- That dead-link family has a specific trigger, and it is not worktree creation: `syncIgnoredPathsIntoWorktree` (`src/workspace/task-worktree.ts`) shares dependencies by mirroring git-ignored paths into each new task worktree as a single directory symlink (`<worktree>/node_modules -> <checkout>/node_modules`). If anything then runs `pnpm install` or `pnpm add` *inside* a worktree, pnpm writes through that symlink into the main checkout's store while computing each link's relative text from the worktree path, so entries become `node_modules/<pkg> -> ../../../.cline/worktrees/<id>/kanban/node_modules/.pnpm/...`. Those resolve fine while the worktree exists and die the moment it is deleted, which breaks the main checkout's next build while an already-running process keeps working until it restarts. Detect with `pnpm run check:links` (`scripts/check-symlinks.mjs`, wired into `pnpm run check` after `typecheck`, so `prepublishOnly` and CI run it): it walks `node_modules`, `web-ui/node_modules` and `packages/*/node_modules`, prints every dead link as `<link> -> <target>`, prints how many are fixable, exits 1 when any are found, and relinks the fixable ones with `--fix` (exit 2 if unfixable links remain). It refuses to scan a `node_modules` that is itself a symlink, so it never writes into a shared install. The raw manual fallback is `find node_modules web-ui/node_modules -type l ! -exec test -e {} \; -print` (must print nothing); repair with `pnpm install --frozen-lockfile` in the main checkout or the relink procedure above, and treat that scan as the source of truth because a relink only holds until the next install rewrites the links relative to whichever directory pnpm ran in. Prefer dependency changes in the main checkout and scan before deleting task worktrees. Turbopack/Next projects are exempt because `listTurbopackNodeModulesSymlinkSkipPaths` makes them copy `node_modules` instead of symlinking it. Installs from inside a task worktree are now blocked at the moment of the mistake by the workspace-root `preinstall` guard (`scripts/guard-worktree-install.mjs`), with `KANBAN_ALLOW_WORKTREE_INSTALL=1` as the escape hatch that requires running `node scripts/check-symlinks.mjs --fix` afterwards.
- Dead worktree links also hide *outside* symlinks entirely: pnpm's `node_modules/.bin` entries are generated shell scripts (regular files) with the target baked into the text (`# cmd-shim-target=` plus the `exec`/`NODE_PATH` lines), so `check:links` cannot see them even though they are just as broken. An install inside a worktree rewrites those shims *in the shared install* to `'../../../../.cline/worktrees/<id>/kanban/node_modules/...'`, and the failure only surfaces later as `Cannot find module '<checkout>/node_modules/<pkg>/...'` for a worktree that may already be deleted (this is what broke `vitest` after worktree `b7ade` was removed, while `check-symlinks.mjs` still reported zero dead links). Detect with `grep -rl 'cline/worktrees' <checkout>/node_modules/.bin <checkout>/web-ui/node_modules/.bin <checkout>/packages/*/node_modules/.bin` (must print nothing). `pnpm install --frozen-lockfile` - even `--force` - treats the tree as "Already up to date" and does not rewrite existing shims, so repair the text directly: set each exec target to the shim's own `# cmd-shim-target=` value (relative to `node_modules/.bin`) and replace the stale `.cline/worktrees/<id>/kanban/node_modules/.pnpm/node_modules` NODE_PATH entry with `<checkout>/node_modules/.pnpm/node_modules`.
- `pnpm --filter <pkg> run <script>` (that is, `pnpm run web:typecheck` / `web:test`) fails in those same provisioned worktrees with `ERR_PNPM_UNSAFE_TASK_RUN_STATE_PATH`, because pnpm 12 keeps per-task state in `node_modules/.pnpm-task-run-state-v1` and refuses to use a `node_modules` that resolves through a symlink. Root-level scripts (`pnpm run typecheck`, `test:*`) still work. Fix the worktree, not the repo: replace the top-level `node_modules` symlink with a real directory of symlinks to the shared install's entries, delete the `.pnpm-task-run-state-v1` symlink from it (so pnpm can create a real directory), and rerun. This reprovisions only the current worktree; the shared install is untouched.
- `pnpm --filter <pkg> run <script>` in a provisioned worktree is worse than the `ERR_PNPM_UNSAFE_TASK_RUN_STATE_PATH` error above: while the worktree's `node_modules` (root *or* `web-ui/node_modules`) is still a symlink, pnpm decides its deps are stale and silently runs a full `pnpm install` (the repo sets no `verify-deps-before-run`), and that install rewrites entries inside the *shared* checkout - `node_modules/.pnpm/node_modules/*` and `web-ui/node_modules/*` - as relative targets into `.cline/worktrees/<id>/kanban/node_modules/.pnpm/...`. Everything keeps resolving while the worktree exists, so neither `pnpm run check:links` nor a dead-link scan reports it, and the install dies the day that worktree is deleted. Provision *both* trees as real directories of symlinks to the shared install before running any `--filter` script, and export `npm_config_verify_deps_before_run=false` so pnpm never installs on your behalf; verify with `find <checkout>/node_modules <checkout>/web-ui/node_modules -type l -lname '*worktrees*'` (must print nothing). Repair by rewriting each target's `kanban/node_modules/` tail under `<checkout>/node_modules` (one occurrence moved 823 hoisted plus 60 `web-ui/node_modules` links). `pnpm install --frozen-lockfile` in the main checkout does *not* rewrite the hoisted `.pnpm/node_modules` layer, so it cannot fix those by itself.
- Both prompt composers (`ClineChatComposer`, `TaskPromptComposer`) are CodeMirror editors, not textareas. Shared behaviour lives in `web-ui/src/components/prompt-composer/`: `prompt-code-editor.tsx` (the wrapper), `use-composer-completion.ts` (`@file` mentions and `/commands`), `use-composer-image-attachments.ts` (paste/drop/remove), and `fence-analysis.ts` (pure fence scanner). Put composer behaviour there, not back in the two components: they were ~1060 lines of near-duplicate keydown, paste and resize handling before, and the four copies of image-paste logic had already drifted.
- Fenced code blocks in the composer are styled by line decorations from `analyzeFenceLines`, which is a deliberate CommonMark *subset* (backtick/tilde, <=3 leading spaces, closing delimiter at least as long). Do not swap in a full markdown parser to "fix" an edge case unless you re-check the auto-close and arrow-navigation rules, which assume line-local scanning.
- Two CodeMirror keymap traps. (a) A key already bound in `defaultKeymap` wins unless your binding is `Prec.highest`/`Prec.high`; the composer's Enter/Shift-Enter/ArrowUp/ArrowDown bindings are `Prec.high` for that reason. (b) Host key policy goes in `Prec.highest(EditorView.domEventHandlers({ keydown }))` rather than a `keymap` entry: `runHandlers` stops at the first binding that returns true, so a `keymap` command cannot both claim the key *and* hand it back. A DOM handler returning true prevents the default, returning false falls through to the keymap.
- Synthetic `KeyboardEvent`s need `keyCode` set for CodeMirror to resolve a keymap binding: `w3c-keyname` maps mods from `keyCode`, so `new KeyboardEvent("keydown", { key: "Enter" })` silently matches nothing and the command never runs. Tests that dispatch key events must pass `keyCode` (see `prompt-code-editor.test.tsx`).
- CodeMirror mounts fine in jsdom, but `Range.prototype.getClientRects` does not exist there. CM's measurement runs from a `requestAnimationFrame` callback, so the resulting `TypeError` arrives as an *unhandled* error attributed to whichever test file happens to be running, not to the editor test. `web-ui/vitest.setup.ts` stubs `getClientRects`/`getBoundingClientRect` and `ResizeObserver`; keep those stubs if you touch the editor.
- A non-wrapping code line inside the editor blows out the whole composer unless `.cm-content` gets `min-width: 0`. `.cm-content` is a flex child, so its automatic minimum size grows to the widest `white-space: pre` line: prose stops wrapping and the tail of long code lines becomes unreachable. jsdom cannot catch this (no layout), so verify composer styling in a real browser, not only with tests.
- Prism token colors for chat code blocks and the diff viewer share one palette in `globals.css` scoped via `:is(.kb-diff-text, .kb-markdown-code)`. Chat fenced blocks had no *theme* for a long time, so they were highlighted structurally but rendered monochrome. Adding a new token-colored surface means adding its class to that `:is()` list; adding colors under only one scope reintroduces the drift.
- Printable-character policy in the composer belongs in `EditorView.inputHandler`, not in a `keymap` entry: keymaps only see `key`/`keyCode`, so they miss IME commits, virtual keyboards and multi-character inserts, and `preventDefault` on a printable keydown bypasses CodeMirror's own input pipeline. The backtick/fence policy (`applyComposerTextInput`) lives there and is exported so tests can call it with a real `EditorView` instead of synthesising DOM input events.
- Do not reach for `Decoration.replace({ block: true })` to collapse the composer's fence delimiter rows: CodeMirror throws `Block decorations may not be specified via plugins`, and plugins may not replace line breaks either. The rows are hidden with an inline replace plus a CSS-thin `.cm-code-cap`, and most markdown syntax is revealed whenever a selection range touches it (that is why the decoration plugin rebuilds on `selectionSet`, not just `docChanged`). Swap positions only with a `StateField`, and re-check that the caret can still reach the info string.
- The *opening* fence delimiter is the exception to "reveal what the selection touches": it stays collapsed while the caret merely sits on its row. `computeFenceAutoPair` leaves the caret at the end of the run so the language can be typed (` ```ts `), and the old touch test matched an empty caret at that boundary, so the three backticks reappeared the instant the block was created. `isDelimiterRevealed` therefore reveals on a non-empty selection that covers part of the run, plus a caret *inside* it (line start still reveals, which is the Home/ArrowUp escape hatch) but not a caret at its end. Consequences: never give the collapsed opener `.cm-code-cap`'s `font-size: 0` — it is the block's header strip (`.cm-code-block-top.cm-code-cap`), it holds the native (undrawn) caret and the language label, and a zero font size collapses the caret; keep its `line-height` stable too, or the block jumps 12px when the caret enters/leaves. The closing delimiter keeps the plain touch rule so it stays deletable, because `computeFencePairBackspaceChange` only special-cases openers.
- The composer's fence auto-pair is stateful in a subtle way: the pair is inserted by the same keystroke that completes the opener, so anything that changes the opener afterwards must keep the closer in step. `computeFenceAutoPair` resizes the paired closer when the run grows, and `computeFencePairBackspaceChange` (bound to `Backspace`) shrinks or removes it; without those, a fourth backtick silently un-closes the block and an orphan closer restyles the rest of the draft as code. Deleting the opener by other means (select-all, cut) is still not reconciled.
- Linked-task auto-start (a review -> Done task unblocking backlog dependents) is owned by `src/server/linked-task-autostart.ts` and has exactly two entry points: the runtime `workspace.saveState` handler (`src/trpc/workspace-api.ts`, wired to `startWorkspaceTaskSession` in `runtime-server.ts`) and the CLI `task done` path (`src/commands/task.ts`). The CLI cannot use the server's in-process starter because sessions live in the server process, so it passes a runtime tRPC adapter to the same service; keep `autoStartedTasks` in its JSON output. The UI must never start unblocked dependents client-side: the server only sees the transition while those tasks are still in `backlog` in the saved board, so starting them (or moving them to in_progress before the save lands) makes the dependency diff skip them or races the server into a duplicate session. The server moves started dependents to in_progress itself and re-broadcasts `workspace_state_updated`, which is what moves the cards; `use-linked-backlog-task-actions.ts` now only requests notification permission and leaves the rest to the server.
- The dependency handoff note (prepended only to the auto-started dependent's kickoff prompt, never written to the card) is built by `src/core/dependency-handoff.ts` with the commit resolved by `src/workspace/dependency-handoff-commit.ts`. Do not "simplify" commit resolution to the prerequisite worktree HEAD: the default commit choreography cherry-picks the task commit onto the base ref, so the worktree HEAD keeps its original sha and is *not* an ancestor of the base ref, which is why resolution has to fall back to `git log <baseRef> --grep=<taskId> --fixed-strings`. Conversely, a worktree the agent never committed in reports the base ref tip as HEAD, so that sha must be rejected or the note falsely claims the base commit as the prerequisite's work. The whole note is gated inside `startReadyDependentTasks` by the global `dependencyHandoffContextEnabled`, read from `loadGlobalRuntimeConfig` there so the CLI and UI paths cannot drift; do not thread the flag through only one caller.
- The expanded Kanban agent sidebar *floats over* the board instead of displacing it, and that only works because `ProjectNavigationPanel` renders a `data-testid="kanban-agent-layout-spacer"` div that holds the sidebar's unexpanded width in the flex row for as long as the fixed overlay frame exists (`keepExpandedFrame`, which also covers the retract animation). Board columns are `flex: 1 1 0` (`board-column.tsx`), so without that spacer they stretch into the vacated space the instant the panel goes fixed and snap back on retract. Do not remove it as "redundant": it is completely covered by the panel (whose width starts at exactly that width), and it must stay mounted until `transitionend`/the fallback timeout so the columns never move in either direction.
- Terminal typography (font size / line height / letter spacing) is a per-browser view preference stored under `kanban.terminal-*` in localStorage, not in `~/.cline/kanban/config.json`, so a laptop and a phone can legitimately differ. `web-ui/src/terminal/terminal-typography.ts` owns the constants, clamping/step-normalising and a small subscribable store; `PersistentTerminal` reads it through `createKanbanTerminalOptions` at creation and subscribes to it so settings changes mutate `terminal.options.fontSize/lineHeight/letterSpacing` on live task + home-shell terminals and then re-run the fit + control `resize` path. Never style `.xterm` with CSS: xterm measures its cell size from its own options, so a CSS font override desynchronises the cursor/selection grid from the PTY cols/rows. A font change makes the shared PTY narrower (fewer columns), and whichever viewer resized last wins; do not add client-side fighting logic for that.
